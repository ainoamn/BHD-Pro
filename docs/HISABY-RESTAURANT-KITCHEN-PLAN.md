# حسابي للمطاعم والمطابخ — وثيقة خطة التنفيذ والتمييز

**التاريخ:** 25 يوليو 2026  
**الحالة:** R1–R4 منفّذة على `main` (صالة · مطبخ · إغلاق مالي عبر POS) + محطات KDS وإلغاء محمي وصرف نقد محمي؛ التالي R5 حجوزات/وصفات.مالي  
**العائلة:** حسابي (محاسبة) · حسابي للكاشير · **حسابي للمطاعم** (منتج ثالث)  
**المستودع:** `ainoamn/BHD-Pro`

---

## 1) الملخص التنفيذي

نخطط لبناء **نظام متكامل لإدارة المطاعم والمقاهي والمطابخ** كمنتج مستقل داخل منصة حسابي، مع **ربط عميق** بنظامي المحاسبة والكاشير الحاليين — بنفس فلسفة الربط بين المحاسبة والكاشير اليوم (`companyId` + تفعيل ربط صريح + مشاركة المحرك المالي والمخزني).

| البند | القرار |
|--------|--------|
| هل هو «إضافة بسيطة على POS»؟ | **لا** — نظام تشغيل كامل للصالة والمطبخ |
| هل يعيد اختراع الفوترة/GL؟ | **لا** — يستدعي محركات المحاسبة والكاشير |
| الهدف التجاري | توسيع حسابي من «محاسبة + كاشير تجزئة» إلى **منصة تشغيل محلية** (تجزئة + ضيافة) |
| أسلوب التنفيذ | موجات قصيرة قابلة للبيع، كل موجة تُغلق بمخرج تشغيلي واضح |

---

## 2) الرؤية والمنتج

### 2.1 ماذا نقدّم؟

**حسابي للمطاعم** = نظام لإدارة:

- الصالة (طاولات، مناطق، نُدُل، حجوزات)
- المطبخ (شاشات تحضير KDS، محطات، حالات الطلب)
- القائمة (أصناف، معدّلات، أحجام، كورسات، توفر)
- الوصفات وخصم المكونات من المخزون
- قنوات الطلب: صالة · سفري · توصيل (على مراحل)
- الإغلاق المالي عبر نفس دفتر حسابي والكاشير

### 2.2 ماذا لا نبني في الموجات الأولى؟

- تطبيق عميل نهائي كامل (طلب من الجوال للضيف) — لاحقاً
- تكامل كل تطبيقات التوصيل دفعة واحدة — لاحقاً موجة قنوات
- نظام موارد بشرية منفصل للمطاعم — نستخدم موظفي الشركة الحاليين أولاً
- محاسبة موازية أو دفتر منفصل — ممنوع؛ مصدر الحقيقة المالية واحد

## 3) الميزات (حسب الطبقة)

### 3.1 الصالة وخدمة الضيوف

| ميزة | الوصف | موجة |
|------|--------|------|
| مخطط صالة | مناطق + طاولات بسعات وحالات | 2 |
| طلب مفتوح على طاولة | إضافة أصناف، ملاحظات، ضيوف | 2 |
| دمج / نقل / تقسيم طاولة | تشغيل يومي للمطاعم | 3 |
| حجوزات | وقت، عدد أشخاص، طاولة | 5 |
| أدوار نادل / كاشير صالة / مدير | صلاحيات منفصلة | 1–2 |

### 3.2 المطبخ (قلب التميّز التشغيلي)

| ميزة | الوصف | موجة |
|------|--------|------|
| KDS متعدد المحطات | مشويات / مشروبات / حلويات… | 3 |
| حالات التحضير | جديد → قيد التحضير → جاهز → مُسلَّم | 3 |
| طباعة مطبخ / تنبيه صوتي | حسب المحطة | 3 |
| أولوية وتأخير | تمييز الطلبات المتأخرة | 4 |
| إلغاء / تعديل بند بعد الإرسال | مع صلاحية / dual-control عند الحاجة | 3–4 |

### 3.3 القائمة والوصفات

| ميزة | الوصف | موجة |
|------|--------|------|
| قائمة مربوطة بمنتجات المخزون | لا كتالوج منفصل بالكامل | 1 |
| معدّلات وإضافات | جبن، حجم، بدون بصل… | 2 |
| وصفات (BOM) | خصم مكونات عند الإغلاق | 4 |
| توفر يومي / نفاد | إخفاء صنف من القائمة | 2 |
| قوائم أسعار (صالة / توصيل) | لاحقاً إن لزم | 5 |

### 3.4 المالية والربط (استهلاك خصائص المنصة)

| ميزة | المصدر | كيف |
|------|--------|-----|
| فاتورة ضريبية / إيصال | المحاسبة + POS | إغلاق طلب مطعم → إنشاء/ترحيل فاتورة |
| طرق الدفع | POS / بوابات | نقد، بطاقة، شريك، رصيد متجر |
| ترحيل GL | `GlPostingService` | نفس مسار بيع الكاشير قدر الإمكان |
| مخزون | منتجات + مستودعات | خصم عبر حركات مخزون / وصفات |
| عملاء | دفتر العناوين | ربط ضيف بجهة اتصال |
| وردية صندوق | POS shifts | محطة دفع المطعم مربوطة بورديات الكاشير |
| إشعارات إيصال | واتساب/إيميل (عند التفعيل) | نفس `CustomerNotifyService` |
| حماية إلغاء/خصم | Dual-control | إعادة استخدام نفس المحرك |

### 3.5 تقارير المطعم (إضافة فوق تقارير المحاسبة)

- مبيعات حسب طاولة / نادل / قناة / ساعة الذروة
- متوسط وقت التحضير (مطبخ)
- هدر / إلغاءات بنود
- ثم التقارير المالية الشاملة تبقى في المحاسبة

## 4) آلية التنفيذ والمعمارية

### 4.1 موقع المنتج في المنصة

```text
                    ┌──────────────────────────┐
                    │     شركة واحدة (Tenant)     │
                    │   companyId مشترك        │
                    └────────────┬─────────────┘
           ┌─────────────────────┼─────────────────────┐
           ▼                     ▼                     ▼
   ┌───────────────┐    ┌───────────────┐    ┌─────────────────┐
   │ حسابي محاسبة  │    │ حسابي كاشير   │    │ حسابي للمطاعم    │
   │ /dashboard    │◄──►│ /pos          │◄──►│ /resto (مقترح)   │
   │ GL · ضريبة    │    │ دفع · وردية   │    │ صالة · مطبخ ·   │
   │ مخزون · تقارير│    │ إيصال         │    │ قائمة · حجوزات  │
   └───────────────┘    └───────────────┘    └─────────────────┘
```

### 4.2 آلية الربط (مثل POS ↔ المحاسبة)

اقتراح حقول على `Company` (عند التنفيذ):

| حقل | الغرض |
|-----|--------|
| `restoLinkedAt` | لحظة تفعيل ربط المطاعم بالشركة |
| `restoEnabled` أو ضمن `apps` | ظهور المنتج في الواجهة |
| مفتاح تقني اختياري | أجهزة صالة/مطبخ إن لزم (مشابه لربط POS) |

**قاعدة ذهبية:** لا يُنشأ مستأجر منفصل للمطعم؛ نفس الشركة، نفس الباقة/الحدود لاحقاً.

### 4.3 تدفق تشغيلي → مالي

```text
1) نادل يفتح طلب على طاولة
2) يضيف أصناف + معدّلات
3) يرسل للمطبخ → يظهر على KDS
4) المطبخ يعلّم «جاهز»
5) الضيافة / الدفع عند الكاونتر أو على الطاولة
6) النظام يستدعي مسار بيع مشترك (POS/Invoices + GL + مخزون وصفات)
7) إيصال للضيف (واتساب/إيميل عند التفعيل) + قيد في المحاسبة
```

### 4.4 طبقات تقنية مقترحة

| الطبقة | التنفيذ المقترح |
|--------|------------------|
| Frontend | مسارات Next تحت `/resto` (+ شاشات KDS بوضع ملء الشاشة) |
| Backend | موديول Nest `resto/` منفصل عن `pos/` مع استدعاء خدمات مشتركة |
| بيانات | جداول: `resto_floors`, `resto_tables`, `resto_orders`, `resto_order_items`, `resto_stations`, `resto_modifiers`, `resto_recipes`… |
| زمن حقيقي للمطبخ | لاحقاً: SSE أو WebSocket؛ الموجة 3 قد تبدأ بـ polling قصير |
| صلاحيات | أدوار جديدة أو أعلام: `WAITER`, `KITCHEN`, `RESTO_MANAGER` (أو صلاحيات داخل الأمن الحالي) |

### 4.5 ما يُعاد استخدامه صراحةً (لا نكرره)

- `InvoicesService` / إنشاء فاتورة مبيعات  
- `PosService` أنماط الدفع والوردية حيث يناسب  
- `GlPostingService`  
- `Products` + `WarehouseStock` + حركات المخزون  
- `Contacts`  
- `DualControlService`  
- `CustomerNotifyService`  
- إعدادات الشركة والضريبة

## 5) خطة الموجات (آلية التنفيذ الزمنية)

### الموجة R1 — أساس المنتج والربط (أسبوعان تقريباً) — **منجزة**

**المخرج:** منتج `/resto` يعمل على نفس الشركة مع ربط صريح.

- هيكل موديول Backend `resto/` + صفحات Frontend `/resto`  
- `restoLinkedAt` + مفتاح `hresto_` + واجهة تفعيل (مطاعم + إعدادات المحاسبة)  
- أدوار: `WAITER` · `KITCHEN` · `RESTO_MANAGER`  
- قائمة أصناف من `GET /resto/menu` (منتجات نشطة)  
- صالة فارغة `GET /resto/floor` (placeholder حتى R2)  
- بطاقة في الصفحة الرئيسية + رابط في الشريط الجانبي

**معيار قبول:** شركة مربوطة ترى قائمة وتفتح شاشة صالة فارغة دون كسر المحاسبة/الكاشير.

### الموجة R2 — الصالة والطلب المفتوح — **منجزة**

**المخرج:** طاولات + طلب حي + إرسال للمطبخ.

- مناطق وطاولات وحالات + تهيئة افتراضية  
- فتح طلب، إضافة بنود، حذف مسودة  
- إرسال للمطبخ + شاشة مطبخ بسيطة (طابور)  
- حالات طلب: OPEN / SENT / PARTIAL / READY / CLOSED  

**معيار قبول:** نادل يكمل طلب طاولة من الفتح حتى الإرسال للمطبخ.

### الموجة R3 — المطبخ المتكامل (KDS) — **أساسي منجز**

**المخرج:** شاشة مطبخ صالحة للوردية الحقيقية.

- محطة مطبخ افتراضية + طابور بنود  
- تحديث حالة البند (تحضير / جاهز / قُدّم)  
- تمييز التأخير بالألوان حسب العمر  
- polling كل ~8 ثوانٍ (SSE لاحقاً)

**معيار قبول:** مطبخ يغلق بنوداً دون الرجوع للصالة يدوياً على ورقة.

### الموجة R4 — الإغلاق المالي + الوصفات — **إغلاق مالي منجز**

**المخرج:** إغلاق طلب = فاتورة POS + مخزون + قيد محاسبي.

- دفع نقد / بطاقة عبر `PosService.createSale`  
- ربط `invoiceId` على الطلب  
- سفري (`TAKEAWAY`) بدون طاولة  
- إغلاق تشغيلي اختياري (`soft`)  
- وصفات BOM — لاحقاً  

**معيار قبول:** تقرير المبيعات يطابق إغلاقات المطعم المدفوعة لنفس اليوم.

### الموجة R5 — نضج تشغيلي — **تقارير تشغيلية منجزة جزئياً**

- ~~تقارير ذروة ووقت تحضير~~ (`/resto/reports` + مركز التقارير)  
- حجوزات  
- سفري / توصيل مبسّط  
- تحسينات UX للنادل والـ KDS  
- Capacitor لاحقاً لأجهزة لوحية إن لزم

## 6) الإيجابيات

| الإيجابية | الأثر |
|-----------|--------|
| مصدر مالي واحد | لا تعارض بين «حسابات المطعم» و«دفتر الشركة» |
| إعادة استخدام POS/المحاسبة | سرعة بناء + جودة ترحيل أعلى |
| منتج ثالث قابل للتسويق | باقة ضيافة / upsell من التجزئة للمحليين |
| تمييز تشغيلي (مطبخ + صالة) | أغلب برامج المحاسبة العربية ضعيفة هنا |
| نفس الهوية والحساب | العميل لا يدير ثلاثة تسجيلات دخول منفصلة |
| مسار واضح للخليج | مقاهي ومطاعم عُمان والمنطقة |

## 7) السلبيات والمخاطر

| السلبية / المخاطر | التخفيف |
|-------------------|---------|
| نطاق كبير إن نُفّذ دفعة واحدة | موجات R1–R5 صارمة؛ لا حجوزات قبل KDS مالي |
| تعقيد UX (نادل + مطبخ + محاسب) | شاشات منفصلة لكل دور؛ لا «شاشة واحدة للكل» |
| تعارض مخزون الوصفات مع بيع POS | قواعد واضحة: وصفة عند إغلاق طلب مطعم فقط |
| أجهزة لوحية / شبكة المطبخ | بدء بمتصفح ملء الشاشة؛ Capacitor لاحقاً |
| ضغط على فريق التطوير | لا موازاة مع موجات محاسبة ثقيلة في نفس الأسبوع |
| توقعات تكامل توصيل فوري | تُدرج صراحة في R5+ وليس الإطلاق |
| تضخم الباقات والتسعير | تسعير منتج مطاعم كإضافة أو باقة ضيافة لاحقاً |

## 8) كيف يفيد المنصة؟

1. **توسيع السوق المستهدف** من متاجر/خدمات إلى ضيافة (مقاهي، مطاعم، كافتيريات).  
2. **رفع القيمة الدائمة للعميل (LTV):** من يستخدم المطاعم سيبقى على المحاسبة والكاشير.  
3. **Upsell طبيعي:** محل فيه كاشير قد يفتح فرع مقهى على نفس المنصة.  
4. **بيانات تشغيل أغنى:** أوقات التحضير والطاولات تغذي لاحقاً مساعد AI بإشراف بشري.  
5. **تعزيز الرواية التسويقية:** «منصة تشغيل محلية عربية» لا مجرد فوترة سحابية.  
6. **إعادة استثمار الكود الحالي:** كل موجة مطاعم تزيد استخدام GL والمخزون والإشعارات بدل كود ميت.

## 9) كيف تُميّز المنصة عن الباقين؟

| المنافسون النموذجيون | ضعفهم الشائع | تمييز حسابي |
|---------------------|--------------|-------------|
| محاسبة سحابية عامة | كاشير ضعيف أو بدون مطبخ | محاسبة + كاشير + **مطاعم/مطبخ** في عائلة واحدة |
| كاشير مطاعم أجنبي | محاسبة خليجية/ضريبة ضعيفة أو تكامل هش | ترحيل عُماني/خليجي أصلي + OTA مسار جاهز |
| أنظمة محلية متفرقة | ثلاثة برامج + Excel | ربط شركة واحدة وتشغيل موحّد |
| تطبيقات توصيل فقط | لا دفتر ولا مخزون وصفي | التشغيل + المالية + المخزون معاً |

**جملة التمييز المقترحة:**  
> حسابي يدير ضيافتك من الطاولة والمطبخ حتى القيد الضريبي — بنفس حساب الشركة، بدون جزر برمجية.

عناصر تمييز ملموسة عند الإطلاق:

- ربط صريح ثلاثي (محاسبة ↔ كاشير ↔ مطاعم)  
- KDS عربي-أولاً مع مسار مالي حقيقي  
- Dual-control على العمليات الحساسة (إلغاء/خصم)  
- إيصالات وقنوات إشعار من نفس البنية التحتية  
- هوية خليجية (لغة، عملة، ضريبة، امتثال)

## 10) التسعير والتعبئة (اقتراح أولي — قابل للتعديل)

| الخيار | الفكرة |
|--------|--------|
| إضافة على باقة احترافي/مؤسسات | «وحدة مطاعم» تُفعَّل للشركة |
| باقة ضيافة | تشمل محاسبة + مطاعم (+ كاشير عند الحاجة) |
| حد أجهزة KDS / طاولات | يُحدَّد لاحقاً حسب التكلفة والدعم |

لا يُثبَّت السعر في هذه الوثيقة؛ يُحسم قبل إطلاق R2 تجارياً.

## 11) معايير نجاح الإطلاق (MVP تجاري)

يعتبر المنتج «جاهزاً لبيتا مطعم حقيقي» عندما:

1. مطعم واحد مربوط يعمل وردية كاملة (فتح طاولة → مطبخ → دفع → قيد محاسبي).  
2. لا فروقات غير مفسّرة بين مبيعات المطعم وتقرير المبيعات اليومي.  
3. المطبخ يعتمد الشاشة دون ورقة لأكثر من أسبوع.  
4. إلغاء حساس محمي بصلاحية/موافقة.  
5. فريق الدعم يملك دليل تشغيل عربي قصير.
