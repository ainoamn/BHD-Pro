# Runbook: النسخ الاحتياطي والاستعادة

## أهداف مقترحة

- قاعدة البيانات: RPO ≤ 15 دقيقة وRTO ≤ 4 ساعات للخطة الإنتاجية.
- المرفقات: versioning ونسخ يومي عابر للحساب/المنطقة حسب المتطلبات.
- Redis cache ليس مصدراً للحقيقة؛ لا تعتمد عليه في الاستعادة المالية.

## النسخ

1. فعّل PITR في PostgreSQL/Neon مع لقطة يومية مشفرة واحتفاظ 35 يوماً على الأقل.
2. خزن نسخة schema/migrations ورقم commit مع كل نقطة إصدار.
3. فعّل S3 versioning، منع public access، تشفير KMS/SSE وسياسة lifecycle.
4. راقب آخر نسخة ناجحة وحجمها وفشلها؛ التنبيه بلا اختبار استعادة غير كافٍ.

## اختبار الاستعادة الشهري

1. استعد إلى مشروع/شبكة معزولة، لا فوق الإنتاج.
2. استخدم أسرار اختبار ولا تسمح بإرسال بريد/webhook حقيقي.
3. شغّل `prisma migrate status` ثم فحوص count/checksum وعينات لشركتين.
4. تحقق من invoice totals/payments/GL، قيود uniqueness، document sequences، والمرفقات.
5. سجل الزمن الفعلي، نقطة البيانات المستعادة، وأي فرق عن RPO/RTO.

## استعادة حادث

- أعلن freeze للكتابة وسجل آخر transaction time المقبول.
- اختر PITR قبل الحدث، استعد في قاعدة جديدة، تحقق، ثم بدّل connection secret بشكل ذري.
- أبق القاعدة القديمة read-only للأدلة؛ لا تحذفها حتى اعتماد الإغلاق وسياسة الاحتفاظ.
- بعد التحويل، أبطل كل sessions إذا كان الحادث متعلقاً بالهوية أو الأسرار.
