# Runbook: الاستجابة للحوادث

## الأولويات

- **SEV-1:** تسرب أسرار، وصول بين شركتين، دفعات مكررة، استيلاء إداري، أو فقد بيانات.
- **SEV-2:** تعطّل واسع، XSS قابل للاستغلال، فشل نسخ احتياطي، أو webhook backlog.
- **SEV-3:** خلل محدود بلا كشف أو فقد مالي.

## أول 15 دقيقة

1. افتح قناة حادث خاصة وعيّن Incident Commander وكاتب timeline.
2. احفظ الأدلة: وقت UTC، request/correlation IDs، الإصدار، IP، user/company IDs، ونسخة read-only من السجلات. لا تنسخ كلمات مرور أو tokens.
3. احتوِ بأقل إجراء: إيقاف مسار/بوابة، إبطال مفتاح API، تجميد حساب، أو خفض الحركة. لا تحذف السجلات.
4. عند الاشتباه بمفتاح: أضف مفتاحاً جديداً، دوّر الخدمة، أبطل القديم، ثم راجع الاستخدام منذ آخر وقت معروف آمن.

## سيناريوهات

### دفعات مكررة

- أوقف fulfillment للبوابة المتأثرة لا checkout كله إن أمكن.
- ابحث عن `idempotency_key` وexternal session/reference مكرر.
- قارن BillingInvoice وPayment وInvoice داخل transaction snapshot.
- لا تُصدر refund تلقائياً؛ راجع مزود الدفع ودفتر GL واعتمد الإجراء مالياً.

### وصول بين مستأجرين

- أبطل جلسة/مفتاح الفاعل وفعّل maintenance على المسار.
- حدد كل company IDs والحقول المكشوفة، واحفظ query/audit evidence.
- أصلح المرشح tenant-bound وأضف regression test قبل إعادة الفتح.
- صعّد لتقييم الإخطار القانوني حسب الدولة.

### تسرب سر

- لا تسجل السر نفسه. ابحث ببصمة جزئية أو canary ID.
- دوّر السر من مزوده، حدّث secret store، أعد التشغيل، ثم تحقق أن القديم مرفوض.
- راجع audit/Sentry/email/CI artifacts وسجل Git. تنظيف السجل لا يغني عن التدوير.

## الإغلاق

يلزم timeline، السبب الجذري، نطاق الأثر، إجراء الاحتواء، دليل التعافي، مالك لكل corrective action، وتاريخ مراجعة postmortem بلا لوم خلال خمسة أيام عمل.
