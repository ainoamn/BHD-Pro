# مراجعة أعمق لبطء المطاعم (موجة 2)

**التاريخ:** 29 يوليو 2026  
**الـ API الحي كان على:** `7df7258` (إصلاح الصالة الخفيفة منشور) — البطء المتبقي من مصادر أخرى.

## ما وجدناه

| الأولوية | المشكلة |
|----------|---------|
| عالية | `PlanFeatureGuard` يستعلم Neon في **كل** طلب `/resto/*` |
| عالية | الشل يعيد `link-status` + الاشتراك عند **كل** تنقل بين صفحات المطاعم (`pathname` في deps) |
| عالية | مطبخ/Expo يستعلمان البنود عبر join `order.companyId` (خطة بطيئة على Neon) |
| متوسطة | قائمة الانتظار تجلب **كل الصالة** كل 15 ثانية |
| متوسطة | Expo يعمل SSE + poll كل 5 ثوانٍ معاً |
| متوسطة | `getLinkStatus` يستدعي `ensureCompanyAppsLinked` (SELECT إضافي) دائماً |
| بنية | Redis غير مفعّل؛ cold start على Render Free ما زال ممكناً |

## الإصلاحات (هذه الموجة)

1. كاش `assertFeature` لمدة 45 ثانية لكل شركة/ميزة  
2. الشل: إزالة `pathname` من effect الربط — مرة واحدة عند الدخول  
3. `getFloor`: شركة + مناطق + طلبات في موجة واحدة؛ حد 200 طلب مفتوح  
4. مطبخ/Expo: طلبات الشركة أولاً ثم البنود بـ `orderId IN (...)`  
5. `GET /resto/tables/free` لقائمة الانتظار بدل floor كامل  
6. Expo: SSE أولاً + poll احتياطي 12s  
7. heartbeat SSE 45s؛ قائمة المحطات بدون ensure عند كل قراءة  
8. قائمة الطعام: قراءة شركة واحدة للمستودع + فترة اليوم  

## مطلوب بعد النشر

- انتظر Render حتى يظهر commit الجديد في `/api/health`
- تحديث قوي على `/resto`
- إن بقي بطء بعد دقيقة من الخمول: غالباً cold start Render — فعّل Redis أو خطط keep-warm أقصر
